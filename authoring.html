Intent.
Authoring Modules Concurrency Merging

Vim-inspired authoring, without a text editor

Intent's editor runs in VS Code. Its keys are short and combine like Vim's, but they act on the program's structure: every key press is one complete change to the program, recorded as an intent.

The cursor is on a node, never between characters

The program is a tree: modules hold types, functions and tasks; functions hold statements; statements hold expressions. The cursor always sits on one node of it, and the keys move through the tree.

  • j goes into a node, to its first child; k back out to its parent; h and l to the previous and next sibling.
  • gg goes to the top, G to the last sibling.
  • / goes to anything by name: a module, group, type, field, variable, function or task.
  • f follows a reference to its declaration, even into another module. Ctrl+O goes back, Ctrl+I forward again.

A verb, then what

Changes start with a letter that says what kind of change, then one that says what to add. You don't need to memorize the whole list: the prefixes do most of the work.

Prompts offer only what's valid

After the keys, the editor asks for what the new node needs: a name, a type, a parameter's kind. Where something is referred to, it offers a list of what can be referred to right there: the variables in scope, the types and functions of the modules this one depends on, the fields of a struct, one level at a time (b, b.velocity, b.velocity.y). There's no way to type a name that doesn't exist, and nothing to parse.

Replacing works the same way. r on a name renames it. The editor knows exactly which names refer to it, scope by scope, so every one of them follows and nothing else with the same spelling changes.

The program

[dependency math]
module physics
{
    struct Body
    {
        Vec2 position;
        Vec2 velocity;
    }

    public fn applyGravity(inout Body body, float dt)
    {
        body.velocity.y = body.velocity.y - 9.8 * dt;
    }
}

The code is never half written: after every key it's a complete program, with empty slots where something is still to come. Each step is an intent in the history, so undo is exact and a merge knows what each change meant.

Rendered, in one canonical order

What you read is rendered from the program: indentation, braces, semicolons and the order of a module's members are the renderer's, not yours. There's no formatting to argue about, and a diff only ever shows real changes. Groups (ag) are headings members are shown under, for when a module grows.
