Modules, lifetime management and hot reload

A module is the unit of code and of state. It says which modules it uses, it starts and stops in a guaranteed order, and its state lives in it for the whole program.

A module

[dependency math]
module physics
{
    struct Body
    {
        Vec2 position;
        Vec2 velocity;
    }

    public fn applyGravity(inout Body body, float dt)
    {
        ...
    }
}
  • Dependencies are explicit. [dependency math] above the module says it uses math. A module sees only the modules it depends on, and the standard library's, like std::io, the same way.
  • Functions and tasks are private unless marked public. Types are visible to the modules that depend on this one.
  • Module variables are the module's state. They're private to it, shared by its functions, tasks and hooks, and exist for the whole program.
  • Names can be paths, like physics::collision: modules that only share a name, not a parent.

The guaranteed order

Every module can have four lifecycle hooks, @create, @init, @deinit and @destroy, and the program's main module has task @main. The runtime calls them, user code never does, in this order. Here app uses physics, which uses math:

  1. @createmathphysicsappevery module, in no promised orderSets up the module's own state. Its dependencies may not be ready yet.
  2. @initmath→physics→appDependencies first: when a module's @init runs, everything it uses is initialized, so it can call it.
  3. @mainappagain while it returns CONTINUEThe program. Its result is the exit code; returning CONTINUE calls it again, like a frame loop. Each call leaves no job running.
  4. @deinitapp→physics→mathDependents first: while a module shuts down, what it uses is still there.
  5. @destroymathphysicsappevery moduleFinal cleanup of the module's own resources.

Only the main module and the modules it depends on, directly or through others, take part. Hooks take no parameters and return nothing, and any other @ name is a build error.

What you can use when

The order is what makes these rules simple, and they hold in every program:

A module variable's start value–NoZero or a constant, set before any @create. Compute other start values in @init.

What goes where

Each layer of a program holds its own kinds of things, and the editor keeps them there: not even a move can put a statement in a module, or a declaration in a block.

LayerHolds
ProjectModules. A build picks the main module, the one whose task @main runs: by default the only module with one.
ModuleDependencies, types (struct, enum), module variables, functions, tasks, lifecycle hooks, C functions to call (extern), groups and comments.
FunctionParameters (plain, in, inout, out) and a return value. Statements: variables, assignments, if, while, for, calls, return, and jobs.
Taskin, out and inout parameters and a return value, and the same statements as a function. A task runs as a job; see Concurrency.
KernelPlanned: like a task, with a body that's the work for one @index. It can't start jobs, and its code is scalar: the compiler widens it.

Hot reload

Hot reload builds on the same order. Between two calls of @main, no user code is on any stack, so any module can be replaced there, even the main one, while the program keeps running.

  1. @deinit of the changed module and of every module that depends on it, dependents first.
  2. Their @destroy.
  3. The changed module's new code is loaded in place of the old.
  4. Their @create, then @init, dependencies first.
  5. @main is called again, now running the new code.

Modules that don't depend on the changed one aren't touched and keep their state: swap the renderer while the simulation carries on. A hot-reload build is a small host and one library per module; calls between modules go through a table the reload swaps, and since Intent has no function pointers, nothing else can hold on to the old code. If a change alters something an untouched module uses, like a public function's signature, the reload is refused with a request to restart.

The lifecycle and @main work today. Hot reload is designed on top of them and is the next step.
