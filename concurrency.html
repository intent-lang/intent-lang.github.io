Concurrency: tasks, jobs and kernels

Concurrency is part of the language, not a library. A task says what to do; a job is one run of it, scheduled when the jobs it depends on are done, with their results wired into it.

Tasks and jobs

A task is declared like a function, with in, out and inout parameters. A job is an instance of a task: its in parameters are bound when it's declared, and its out parameters are filled when it finishes. Jobs can be declared in any function or task, including @main.

task readFile(in string path, out int status)
{
    ...
}

task processData(in int status, out int result)
{
    ...
}

task writeResult(in int result)
{
    ...
}

public task @main() -> int
{
    job reader = readFile("input.txt");
    job processor = processData().dependOn(reader);
        // wire: reader.status -> processor.status
    job writer = writeResult().dependOn(processor);
        // wire: processor.result -> writer.result
    reader.run();
    writer.waitOn();
    return 0;
}

Dependencies, and the wires between them

dependOn says a job starts only when another is done. When an out parameter of the first and an in parameter of the second have the same name and type, the value is wired across: nobody copies results by hand, and the editor shows each wire under the job.

  • A job can depend on several jobs (fan-in), and several jobs on one (fan-out).
  • A struct output wires to an input of the same struct type, so a whole World can flow from one job to the next.
  • Arrays are shared by reference: a job that's wired to another gets the same array, not a copy.
  • Declaring the graph never blocks. Only waitOn() does.

Mistakes the compiler catches

A graph that would never run, or would hang, doesn't build:

MistakeBuild error
A job without dependencies that's never startedjob 'reader' is never started; call reader.run()
Waiting before the chain is startedwaiting on 'writer' would never end: 'reader' isn't started; call reader.run() before
Starting a job that has dependencies'processor' starts by itself when the jobs it depends on are done; run those instead
Starting the same job twice'reader' is already started

A frame loop

@main returns CONTINUE to be called again. With the standard task delay, frames start a fixed time apart:

public task @main() -> int
{
    job tick = delay(0.016);
    job frame = simulate(world).dependOn(tick);
    tick.run();
    frame.waitOn();
    if (running)
        return CONTINUE;
    return 0;
}

The thread model is a build decision

A program doesn't say how many threads it runs on. The same code can be built to run on a single thread, or on a pool of workers pinned to cores. That's chosen by the build, not written in the code:

{
  "main": "app",
  "hotReload": true,
  "threads": { "mode": "pool", "workers": 4, "affinity": [2, 3, 4, 5] }
}

Jobs compile to MLIR's async dialect and on to native code through LLVM. Today they run on MLIR's async runtime, a thread pool; Intent's own runtime behind the same interface is what lets the build choose.

Kernels

For data-parallel work, a kernel is a task whose body is the work for one element, @index. A job runs it over a range, and the compiler runs many indices at once: in SIMD lanes, and across several jobs.

public kernel simulateObjects(inout ObjectState state)
{
    Object o = state.getObject(@index);
    o.simulate();
    ...
}

public task @main() -> int
{
    job sim = simulateObjects(state) over count;
    sim.run();
    sim.waitOn();
    return 0;
}
  • A kernel is a task, as far as possible: declared next to tasks, public or not, with in, out and inout parameters. Its jobs take part in the graph like any other: dependencies, wiring, run() and waitOn().
  • The range comes from the job: over count runs the body for @index from 0 to count - 1.
  • The code stays scalar. The body is ordinary code for one element, and the compiler widens it to vectors. There are no vector types to learn.
  • The data is laid out for it already: an array of structs is stored as one array per field, the layout SIMD wants.
  • A kernel can't start jobs.

Tasks, jobs, dependencies and wiring work today, built and run as native executables. Build profiles and kernels are designed, and arrays laid out for kernels are done.
